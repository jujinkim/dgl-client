# 공통 코어·모바일 UI·데스크톱 UI 분리 작업 계획

작성일: 2026-10-24. 상태: R1 기능·계약과 성능 분리, R2–R5 기능 우선 구현 중.
기준 코드: `53f1ed4c689c9e8e209987fb01401ce3bcdff78b` (`main`).

## 이번 실행 범위 변경 (2026-10-24)

사용자 후속 지시에 따라 **현재 Mac과 Android API 36 전용 AVD만 검증**한다.
시스템 조회상 현재 Mac은 macOS **26.6.2 (25G83), Apple M1**이다. macOS 14 검증으로
표시하지 않는다. Windows/Linux/macOS 14/Android 34·35 검증은 이번 실행에서 제외한다.
2026-10-24 후속 지시에 따라 **Windows 검증 제외와 빌드 환경 제공은 분리**한다.
Windows Rust 앱의 MSVC 빌드·ZIP 패키징·수동 CI는 유지하며 [Windows 안내](WINDOWS.md)를 따른다.
아래 원래 제품 범위와 Android 네 ABI 보존 요구는 유지하지만 이 환경들의 지원 완료를
주장하지 않는다. 이번 R2 이후 인수 게이트의 환경 범위도 현재 Mac/API36으로 좁힌다.

R1 산출물: [기능 대조표](migration/FEATURE_MATRIX.md), [코어 계약](migration/CORE_API.md),
[성능 계약·도구](migration/PERFORMANCE.md), [기준선·미완료 항목](migration/R1_BASELINE.md).
R1 성능 계측은 미완료 상태로 보존하며 R2–R5 기능 구현의 선행 게이트에서 분리한다.

후속으로 API36 테스트 전용 Perfetto 표시 훅을 구현하고 짧은 검증을 완료했다. 정확한 첫
입력 표시·전체 표본/시나리오·오버헤드·Mac GUI 계측은 남아 있다. [다음 작업](../NEXT_WORK.md)을 따른다.

## 이번 후보 완료 범위 (기존 단계 설명보다 우선)

- Mac: GPUI + alacritty_terminal, Rust russh 코어. Android: Compose/xterm.js + UniFFI.
- 선택한 tmux 패널 하나를 표시한다. 다중 패널 동시 표시·프로젝트·워크스페이스는 제외한다.
- 중성 배경·청록 강조, 시스템/밝은/어두운 테마, 4/8/12/16/24 간격을 사용한다.
- Mac은 좌측 계층·상단 연결 탭, Android는 호스트/터미널 화면·연결 선택기·tmux 하단 시트를 사용한다.
- 빈 목록·연결/신뢰/복구/오류·포커스/비활성 상태, 긴 이름·작은 화면·키보드 표시를 검증한다.
- 후보 테스트 데이터는 기존 영역과 분리한다. 사용자 후속 지시 “legacy는 불필요”에 따라 Android 엔진은 Rust만 제공한다.
- R1b 성능·최적화, 실제 Codex/Claude, R6 데이터 이전은 후속이다. R7의 이전 실행 경로 제거는 이번에 수행한다.
- GUI 실행 불가는 기능 실패도 검증 통과도 아니다. 화면 미검증 상태를 명시한다.

## 1. 목적과 결정 상태

공통 코어, 모바일 UI 로직, 데스크톱 UI 로직을 분리한다. 데스크톱은 Windows·macOS·Linux를
하나의 툴킷으로 지원하고, 제품 목표는 **가볍고, 시각적으로 완성도가 높고, 빠른 앱**이다.
코어 언어는 Kotlin으로 제한하지 않는다.

| 구분 | 내용 | 상태 |
|---|---|---|
| 구조 | 공통 코어 / 모바일 UI / 데스크톱 UI 분리 | 사용자 요구 |
| 데스크톱 범위 | Windows / macOS / Linux | 사용자 요구 |
| 품질 | 작은 자원 사용량, 세련된 화면, 빠른 입력·화면 반응 | 사용자 요구 |
| 공통 코어 | Rust 라이브러리 | 후보 구현·120 fixture 및 격리 SSH 통과 |
| 데스크톱 UI | GPUI | 우선 검증 후보, 채택 미확정 |
| SSH | `russh` 0.64.1 | 비밀번호·RSA·Ed25519·암호화 키 및 두 tmux 버전 통과 |
| 데스크톱 터미널 | `alacritty_terminal` 기반 엔진과 별도 화면 구현 | 우선 검증 후보 |
| 모바일 | Compose/xterm.js + UniFFI 0.32.2 | 후보 엔진·모바일 화면 구현, API36 검사 |

Android 실행 경로는 Rust로 교체했다. 이 변경을 전체 기능 인수나 후보 기술의 성능이
입증됐다는 뜻으로 해석하지 않는다. iOS와 새로운 제품 기능은 이번 계획의 필수 범위에 추가하지 않는다.

초기 요구사항의 KMP/Compose 우선 방향은 이번 사용자 요구에 맞춰 재평가한다.
[원문 요구사항](../KICKOFF_PROMPT.md)은 보존하고,
[ADR 001](decisions/001-architecture.md)은 기존 구현의 결정 기록으로 유지한다.
후보 검증 후 새 ADR에 최종 선택과 비교 결과를 기록한다.

## 2. 변경 규모와 현재 자산

규모는 **대형 아키텍처 전환**이다. UI 파일 분리만으로 끝나지 않으며, Rust를 채택하면
JVM 엔진 이식·SSH 라이브러리 교체·모바일 바인딩·데스크톱 터미널·패키징이 포함된다.
현재 기능과 회귀 시나리오를 명세로 활용해 단계적으로 전환한다.
작업 기간은 아래 R2의 실제 구현·검증 결과 이후 산정한다.

| 현재 위치·역할 | 전환 범위 | 보존할 자산 |
|---|---|---|
| `app/src/commonMain/.../core` | 모델·tmux 파서·명령·입력 인코딩 이식 | 바이트 경계, 인용, 크기 상한, 오류 처리 규칙 |
| `app/src/referenceTest/.../ClientModel.kt`, `tmux`, `ssh` | 연결·복구·스냅샷·SSH 엔진 이식 | 순서·세대 관리와 실제 SSH/tmux 회귀 시나리오 |
| `app/src/jvmSharedMain/.../ui` | 공유 화면을 모바일/데스크톱 프레젠테이션으로 분리 | 호스트·세션·창·패널·설정의 기능과 조작 의미 |
| `app/src/desktopMain` | GPUI 앱·터미널·OS 연동 구성 | Windows DPAPI와 종료 동작의 요구사항 |
| `app/src/androidMain`, `androidApp` | Rust 바인딩 연결, 모바일 수명주기 유지 | Keystore, IME, 단축키·매크로, 볼륨 키, 회전·복귀 동작 |
| 저장소·설정 | 읽기 호환·마이그레이션·복귀 검증 | 호스트 ID, 신뢰 지문, 자격 증명 참조, 설정 |
| 빌드·검증·배포 | Cargo/NDK·3개 데스크톱 빌드와 수집 경로 추가 | 검증 증거, 라이선스·해시·산출물 추적 방식 |

기존 Kotlin 테스트 코드를 Rust에서 그대로 실행할 수는 없다. 입력·기대 결과와 실패 재현을
언어 중립 fixture 또는 Rust 테스트로 옮기고, 실제 SSH/tmux 시나리오로 동등성을 확인한다.
기존 구현도 미검증 항목이 있으므로 기존 동작 전체를 정답으로 가정하지 않는다.
현황은 [검증 문서](VALIDATION.md)와 [작업 목록](../TASKS.md)을 기준으로 한다.

## 3. 목표 경계

```text
Desktop UI (Windows / macOS / Linux)   Mobile UI (우선 Android)
           │ Rust API                         │ UniFFI
           └────────────────┬─────────────────┘
                      공통 코어 (Rust 후보)
        SSH / tmux / 연결 복구 / 상태 / 명령 / 출력 흐름 제어
                            │
            플랫폼 어댑터: 보안 저장 / 파일 / OS 기능
```

- **코어:** 연결·인증·호스트키·tmux 상태·재접속·명령 순서·입출력 상한을 소유한다.
  UI 프레임워크, 창, Compose 상태, GPUI 엔티티, JNI 타입을 공개 API에 넣지 않는다.
- **데스크톱 UI:** 탭·분할 레이아웃·사이드바·명령 팔레트·메뉴·포커스·키보드·마우스·
  창 상태·애니메이션을 소유한다. 명령 팔레트 등 새 표현은 기존 동작을 노출하는 범위로 한정한다.
- **모바일 UI:** 화면 전환·터치·IME 배치·단축키·볼륨 키·접기·회전·백그라운드 수명주기를
  소유한다. 데스크톱의 화면 구조를 모바일에 강제하지 않는다.
- **터미널:** 프로토콜 출력과 화면 렌더링을 구분한다. 데스크톱은 Rust 터미널 엔진을
  검토하고 Android는 초기 전환 동안 기존 xterm.js를 유지할 수 있다.
  `alacritty_terminal`은 완성된 GUI 위젯이 아니므로 렌더링·선택·IME 연결 비용을 포함한다.
- **플랫폼 어댑터:** Windows DPAPI, Android Keystore, macOS Keychain, Linux 보안 저장소를
  각각 평가한다. macOS·Linux의 현재 메모리 전용 개발 모드를 제품용 저장소로 간주하지 않는다.
  보호 저장을 사용할 수 없을 때 평문 저장으로 대체하지 않는다.

Rust 코어는 앱 안에서 로드하는 라이브러리로 계획한다. 원격 데몬이나 별도 상주 서버를
추가하지 않는다. 데스크톱은 직접 호출하고 모바일만 바인딩 경계를 거친다.
원격 프로세스와 세션의 기준은 계속 tmux다.

API에는 명령·상태 이벤트·터미널 출력·오류 종류를 구분한다. 입력/출력은 묶음 전달과
제한된 큐를 사용하고 역압력, 연결·패널·크기 세대, 순서, 취소, 종료, UI 스레드 전달 규칙을
정의한다. 언어 경계를 넘는 객체·버퍼의 소유권과 구독 해제도 계약에 포함한다.
코어는 오류 코드와 구조화된 진단을 제공하고 표시 문구는 UI가 결정한다.

## 4. 기술 선택을 확정하는 검증

R2에서 실제 SSH 터미널 하나, 호스트키 확인, 세션 선택, 사이드바와 탭으로 구성한
작은 앱을 만든다. 검증한 프로토타입 부분은 후속 코어로 정리할 수 있게 독립시킨다.
전체 기능 이식 전에 다음 질문에 답한다.

1. GPUI가 세 OS에서 한글 조합·삭제·후보창 위치·붙여넣기·선택·포커스를 처리하는가?
2. Rust SSH 구현이 기존 비밀번호, RSA/Ed25519, 암호화 개인키, 호스트키 검증을 만족하는가?
3. 터미널 엔진이 Unicode 폭·색상·커서·alternate screen·resize·tmux 복원을 처리하는가?
4. 출력이 몰릴 때도 입력·스크롤·탭 전환이 반응하며 버퍼와 메모리가 제한되는가?
5. Android에서 Rust 라이브러리 로딩·이벤트·취소·종료·Keystore 어댑터 연결이 성립하는가?
6. 최소 지원 OS·CPU·GPU 및 Linux 배포판/디스플레이 환경에서 빌드·실행할 수 있는가?

GPUI는 현재 1.0 이전이며 API 변경이 잦을 수 있다. 버전 또는 커밋을 고정하고
UI 프레임워크 종속 코드를 데스크톱 모듈에 한정한다. 필수 입력·렌더링·배포 조건을
만족하지 못하면 Iced 또는 Tauri+xterm.js를 같은 시나리오로 비교한다.
Tauri의 설치 파일 크기와 실행 메모리는 별도로 측정하며 WebView 프로세스를 포함한다.
Rust나 GPU 렌더링 채택만으로 성능 통과를 선언하지 않는다.

기술 조사 근거(2026-10-24 확인):

- [GPUI 구조와 데스크톱 백엔드](https://gpui.rs/examples/), [개발 상태](https://github.com/zed-industries/zed/tree/main/crates/gpui)
- [UniFFI의 Kotlin 등 바인딩 지원](https://mozilla.github.io/uniffi-rs/latest/)
- [russh](https://github.com/Eugeny/russh), [alacritty_terminal API](https://docs.rs/alacritty_terminal/latest/alacritty_terminal/)
- [Iced](https://github.com/iced-rs/iced), [Tauri 프로세스 모델](https://v2.tauri.app/concept/process-model/)

## 5. 품질 목표와 측정

아래 기준은 사용자 구현 계획에 따라 **R1에서 고정**했다. Android는 같은 API36 AVD·시나리오에서
기존 대비 지연·메모리 증가 10% 이내다. [측정 계약](migration/PERFORMANCE.md)에 장비·표본 수·
정의를 고정했다. 실측값이나 배포 보장은 아니다. 기준은 R2 후보 비교 전에 고정하고,
결과를 통과시키기 위해 사후 완화하지 않는다. 기준을 바꾸면 이유와 기존 결과를 함께 남긴다.

| 항목 | 고정 기준·측정 조건 |
|---|---|
| 기동 | release 빌드, 실행 요청부터 첫 입력 가능한 창까지 p95 1초 이내. 네트워크 접속은 별도 측정 |
| 로컬 입력 반응 | 키 이벤트부터 로컬 화면 반영까지 p95 33ms 이내. SSH 왕복 지연과 분리 |
| 화면 움직임 | 기준 장비 60Hz에서 스크롤·분할 크기 변경·전환의 p95 프레임 시간 16.7ms 이내 |
| 유휴 CPU | 연결 1개·출력 없는 터미널 1개, 안정화 후 60초 평균을 한 코어 기준 1% 이하 |
| 메모리 | 같은 유휴 조건에서 앱 프로세스 전체 상주 메모리 150MiB 이하. GPU 메모리 별도 기록 |
| 설치 크기 | 최종 release 패키지 다운로드 ≤50MiB, 설치 ≤150MiB, 분리 기록 |
| 출력 부하 | 동일 출력 fixture에서 처리량·입력 지연·프레임·메모리를 함께 측정. 출력 누락·순서 오류·무제한 큐 없음 |
| 장시간 안정성 | 재접속·화면 재생성 후 프로세스·스레드·핸들/FD·버퍼 회수. 기존 자원 검증 시나리오와 연결 |

OS·CPU·GPU·RAM·전원 모드·디스플레이·빌드 모드·커밋·테스트 횟수를 기록한다.
기동의 cold/warm 조건, 상주 메모리의 OS별 측정 정의, 입력 시간의 시작/종료 지점,
프레임 수집법과 도구 오버헤드를 R1에서 명시한다. 서로 다른 메모리 지표를 같은 값처럼
비교하지 않는다. 기존 JVM 앱과 후보는 같은 장비·같은 시나리오에서 비교한다.
기존 앱을 실행할 수 없는 환경은 후보의 절대 기준으로 판단하고 비교 불가를 표시한다.

시각적 완성도는 기본 테마만 바꾸는 것으로 완료하지 않는다. 타이포그래피·간격·색상·
선택/포커스/오류 상태·아이콘·짧은 전환 효과를 하나의 디자인 규칙으로 정리한다.
Windows 배율, macOS Retina, Linux 배율별로 잘림·흐림·클릭 영역을 확인하고,
키보드 탐색과 움직임 감소 설정을 포함한다. 애니메이션 때문에 터미널 입력을 지연시키지 않는다.

## 6. 보존해야 할 동작과 데이터

- tmux 3.3a/3.7c 통합 시나리오, 외부 tmux 조작 반영, 일반 SSH fallback과 탐지 실패 상세 안내.
- 최초 호스트키 확인, 저장된 키 변경 차단, 잘못된 인증 시 중단, 보호 저장 실패 시 저장 중단.
- snapshot/live 출력 순서, UTF-8 분할, 입력 바이트 인코딩, 크기 상한, 세대가 다른 결과 폐기.
- 재접속 중 입력 차단·입력 재전송 금지, 사라진 세션 자동 대체 금지, 동일 원격 PID 유지.
- tmux 모드의 정상 연결 종료는 tmux 클라이언트만 종료하며 원격 세션·프로세스는 유지.
- 삭제 명령은 대상 확인을 거치며 호스트·세션·창·패널 이름을 안전하게 처리.
- 호스트 편집·즐겨찾기·최근 접속·독립 연결, 테마·폰트·단축키·매크로·Android 볼륨 키 설정.
- 실제 Codex/Claude TUI와 물리 IME는 별도 인수 항목이며 기존 합성 테스트로 통과를 대신하지 않음.

`settings.json`의 기존 기본값·필드·ID·자격 증명 참조를 fixture로 고정한다.
Windows의 `.sealed`와 Android의 Keystore 암호문은 기존 OS 사용자/앱 경계 안에서 읽는다.
Android 앱 ID는 `kim.jujin.dglc`이며 이전 `kim.jujin.rovessh` 앱과 별도로 설치된다.
Keystore 별칭 `kim.jujin.rovessh.credentials.v1`은 유지하지만 앱 경계가 달라 이전 앱의 키·데이터에
접근하지 않는다. 키를 내보내거나 평문 중간 파일로 옮기지 않는다.

초기 후보 앱은 별도 테스트 데이터 경로를 사용한다. 데이터 전환은 복사본으로
구형 읽기·신형 저장·실패 중단·기존 앱 복귀를 검증한 뒤 적용한다.
호환되지 않는 새 형식은 버전을 명시하고, 백업·복귀 경로가 검증되기 전 원본을 덮어쓰지 않는다.
기존/신규 앱이 동일 설정을 동시에 쓰지 않도록 한다.

기존 지침대로 Windows 실기 검증은 사용자 담당이며 자동 CI 결과로 대신하지 않는다.
이번 범위의 필수 검증이 남으면 R2 전체를 통과 처리하거나 GPUI를 최종 확정하지 않는다.
후보 실패는 코어/UI 경계를 유지한 채 툴킷 재평가로 연결한다.

각 작업 완료 시 코드 커밋, 환경, 명령, 기대/실제 결과, 보고서 경로와 미검증 항목을 남긴다.
이전 엔진은 `app/src/referenceTest`에서 회귀 증거와 테스트용 SSH 관리에만 사용한다.
프로덕션 APK·Mac 실행과 패키징에 포함하거나 대체 엔진으로 노출하지 않는다.
이 지시는 이전의 R7 전 코드 보존·legacy 기본값 규칙보다 우선한다.

## 8. 실행·검증 운영

- 모든 구현·수정·커밋은 현재 운영 지침에 따라 `main`에서 수행한다. 새 작업 브랜치를 만들지 않는다.
- 현재 Android/JVM 빌드는 전환 중에도 재현 가능하게 유지한다. Cargo 모듈의 실제 위치와
  실행 명령과 산출물은 [후보 기록](migration/CANDIDATE.md)에 기록한다.
- 기존 자동 CI 범위를 임의로 확대하지 않는다. Rust 도입 시 변경 경로별 빠른 검증과
  3개 데스크톱 패키징·실기 검증의 실행 조건을 R6에서 정리한다.
- 검증은 CLI·테스트·로그를 우선한다. IME·표시·애니메이션 등 화면 검증이 필요한 항목만
  목적과 종료 조건을 정해 짧게 수행한다.
- 보고서에는 자격 증명·개인키·실제 터미널 원문을 저장하지 않는다. 테스트용 서버와 데이터를 사용한다.
- 라이선스·의존성·보안 검증은 새 Rust/네이티브 배포에 맞춰 갱신한다. 서명·공개 배포 상태는
  실제 결과만 기록한다. 이번에는 개발용 후보 패키지만 만들며 공개 배포는 수행하지 않는다.
- `.dashboard-props.json`은 실제 구현·문서·산출물 변경에 맞춰 갱신하고 검증한다.
  Rust·macOS·Linux를 계획만으로 현재 구현 언어·배포 플랫폼에 등록하지 않는다.

## 9. 다음 작업의 산출물

R1의 기능 대조표와 API/데이터 계약을 사용해 기능·기본 디자인을 우선 구현한다.
그 결과로 R2의 제한된 세로 구현 범위를 고정한다. 첫 구현의 성공 조건은
**실제 SSH 연결 → tmux 선택 → 터미널 입력/출력 → 연결 종료/재접속**, 그리고
현재 Mac의 필수 입력 경로와 API36 Android 바인딩의 성립을 확인하는 것이다.
필수 기능과 기본 화면 검증을 완료해야 후보 완료로 판정한다. 성능·실제 에이전트 인수는 후속이다.
